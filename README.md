# Interpretable ANFIS for Detection of Existing Clinical Bovine Mastitis

Soft Computing project (M.Tech, VIT-AP). Problem statement SIH26109.
Goal: detect existing clinical mastitis from udder sensor readings with a **rule-based, explainable** ANFIS and compare it with other ML methods.

## Quick start (new collaborator: 15 minutes)

```bash
git clone <repo-url> && cd mastitis-anfis
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# get clinical_mastitis_cows.csv from your teammate (or the Mendeley page) and put it in data/raw/
python test_modules.py      # 4 x OK expected
python data_prep.py         # Module 1  -> data/processed/, reports/figures/fig1-7
python baselines.py         # Module 2  -> reports/baseline_results.csv
python train_anfis.py       # Modules 3-5 -> reports/anfis_results.csv, comparison.csv, rules, fig9-10
```

Same random seeds everywhere, so **you should get exactly the same numbers as your teammate.** If not, tell them: that is a bug worth finding.

## Pipeline

```
raw CSV -> data_prep.py (drop leakage, cow-grouped split, 2 indices, train-only scaling)
        -> baselines.py (LogReg / Tree / RandomForest)            \
        -> subtractive_clustering.py (rules from data) -> anfis.py (hybrid learning) -> explain.py
                                                                   /  compared in reports/comparison.csv
```

## Research web application

The primary demonstration is a React + TypeScript frontend served by the FastAPI backend. Both run locally from one command:

```bash
python serve.py
```

Open `http://127.0.0.1:8000`. If the compiled frontend is missing, the launcher uses Node.js/npm to install the declared frontend packages and build it before starting the API. For a manual frontend build:

```bash
cd frontend
npm install
npm run build
```

The seven connected screens are Overview, Clinical detection, Fuzzy reasoning, Synthetic onset study, Model evaluation, Reports, and Methodology. Clinical inference and explanations call the existing Python modules and saved R8/R13 artifacts. The separate FC7 study uses the saved model and computer-generated rows from `data/external/Synthetic_Data_for_Mastitis_Disease/`; its scores are not real-animal or farm evidence, and no future observations are generated by the interface.

The API endpoints are:

| Endpoint | Purpose |
|---|---|
| `GET /api/health` | Application and saved-model availability |
| `GET /api/model/schema?mode=Sensor-only` | Model feature order and learned input ranges |
| `POST /api/predict` | Existing clinical-status model inference |
| `POST /api/explain` | Actual activated rules and explanation values |
| `GET /api/forecast/cows` | Eligible held-out synthetic-study rows |
| `POST /api/forecast` | FC7 score for an eligible synthetic observation |
| `GET /api/results` | Metrics loaded from `reports/final/` and `reports/forecast/` |
| `POST /api/report` | Download a PDF explanation for an actual clinical-model input |

The interface does not prefill invented cow measurements. It shows the feature order and training limits from the saved model scalers; out-of-range values are clipped by the existing Python inference path and displayed with their original and adjusted values. Scores are not calibrated clinical probabilities or diagnoses.

The source `app.py` Streamlit dashboard is retained as a compatibility view. Its detection and generated-data sections continue to use the same Python research modules; Streamlit remains in `requirements.txt` so this existing view and its smoke test stay usable.

To check the API and existing model paths:

```bash
python test_api.py
python test_modules.py
python test_app_core.py
python test_explain_report.py
python test_forecast.py
python test_dashboard_ui.py
```

Evaluation values are read from `reports/final/summary_pooled.csv` and `reports/forecast/forecast_summary.csv`; see `reports/final/RESULTS.md` and `docs/CLAIMS.md` for the evidence and its limits. The working clinical CSV's Version 2 provenance is unresolved, there is no external farm validation, and the synthetic-study metrics are not real-farm validation. See [docs/UI_DESIGN_AUDIT.md](docs/UI_DESIGN_AUDIT.md) for the UI reference audit.

## Team workflow

- `main` always runs. Never commit straight to `main`; use a branch `feat/<what>-<name>` and a pull request.
- The OTHER person reviews and merges. Reviewing means you can explain the change in 5 minutes.
- Raw data is not committed (`.gitignore`); share it by Drive/WhatsApp.
- Numbers on slides or in the paper must come from files in `reports/`. No invented numbers, no invented citations.
